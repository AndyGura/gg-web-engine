# GG-Web-Engine Milestones (Public Roadmap)

Note: This roadmap was AI-generated by Junie (JetBrains autonomous programmer) on 2026-02-25, based on the current repository state and README. It is intended to evolve with community feedback.

## How to read this document
- Milestones are incremental and build on each other.
- Each milestone lists objectives, key deliverables, acceptance criteria, and rationale/risks.
- Issues/PRs should reference the milestone and deliverable IDs where possible.

---

## M0 — Project Hygiene and Contributor Experience
Objectives
- Establish clear contribution and maintenance processes to make the project easy to onboard, develop, and release.

Key Deliverables
- D0.1: Contributor Guide (`CONTRIBUTING.md`) with branching, commit, PR, code review, release process.
- D0.2: Code of Conduct (`CODE_OF_CONDUCT.md`).
- D0.3: Issue/PR templates (`.github/ISSUE_TEMPLATE/*`, `PULL_REQUEST_TEMPLATE.md`).
- D0.4: Monorepo scripts for dev/build/test/publish (npm scripts + `pnpm`/`npm` guidance).
- D0.5: Basic CI (lint, build, unit tests) on PR and main.
- D0.6: Packages versioning policy and changelog standard (Conventional Commits + `CHANGELOG.md`).

Acceptance Criteria
- Running `npm run build` and `npm run test` succeeds on CI for all packages.
- New contributors can follow the guides to set up and submit a PR within 30 minutes.

Rationale/Risks
- Improves trust and velocity; minimal technical risk.

## M1 — Architecture Baseline and Type Safety
Objectives
- Stabilize the core abstractions (World, Entities, Components, Loaders) for both 2D and 3D.
- Increase type-safety and reduce tight coupling.

Key Deliverables
- D1.1: Formalize core interfaces and layering diagram in `docs/architecture/core.md`.
- D1.2: Dependency boundaries: base ↔ 2D ↔ 3D packages; rendering and physics behind facades.
- D1.3: Remove non-null assertions and introduce optional chaining where appropriate.
- D1.4: Introduce lightweight dependency injection for swappable modules (factory/loader registries).
- D1.5: Unified event bus abstraction to avoid direct RxJS leakage across modules.

Acceptance Criteria
- Public API surface for core packages is documented and type-stable.
- 2D/3D modules compile without `!` non-null usage in public paths.

Rationale/Risks
- Enables future feature work; risk of minor breaking changes (covered by M0 release policy).

## M2 — Loading and Serialization Pipeline (2D/3D)
Objectives
- Provide a consistent level/scene loading story across 2D/3D with JSON+GLB+Meta.

Key Deliverables
- D2.1: Unify `level-loader` contracts across base/2D/3D.
- D2.2: Document Level JSON Schema in `docs/specs/level-json.schema.json` and guide.
- D2.3: Deterministic transform application (fix rotation composition FIXME in 3D loader).
- D2.4: Caching strategies documented and benchmarked; add eviction policy.
- D2.5: Export/serialize selected runtime state back to JSON for savegames.

Acceptance Criteria
- Example levels load identically between engines where applicable; rotation math verified with tests.
- Schema validation passes in CI for example levels.

Rationale/Risks
- Reduces user friction; math correctness is critical.

## M3 — Rendering and Physics Parity (Adapters)
Objectives
- Ensure feature parity and predictable behavior across supported engines.

Key Deliverables
- D3.1: Rendering facade consistency: materials, lights, cameras, post-processing hooks.
- D3.2: Physics facade consistency: bodies, triggers, raycast vehicles, materials.
- D3.3: Cross-engine conformance tests (golden tests per feature).
- D3.4: Shared debug overlays (physics wireframes, bounds) pluggable per renderer.

Acceptance Criteria
- The same sample code runs on at least two renderers and two physics engines with matching outcomes within tolerance.

Rationale/Risks
- Smooth engine swaps; requires careful abstraction design.

---

## M4 — Performance and Scale
Objectives
- Optimize for larger scenes and lower-end devices.

Key Deliverables
- D4.1: Object pooling for transient objects and components.
- D4.2: Spatial partitioning (BVH/quad/oct-tree) utilities for culling and broadphase hints.
- D4.3: Instanced rendering support in 3D adapters; batched sprites in 2D.
- D4.4: Optional Web Workers for physics steps; main-thread sync protocol.
- D4.5: Level-of-detail (LOD) utilities with heuristics.

Acceptance Criteria
- Benchmarks in `packages/bench` show >25% improvement on defined scenarios.

Rationale/Risks
- Significant QoS improvement; complexity in threading and determinism.

## M5 — Input and Interaction System
Objectives
- Provide a unified, extensible input layer for keyboard/mouse/gamepad/touch.

Key Deliverables
- D5.1: Input devices abstraction and events.
- D5.2: Bindings/mapping layer with user remapping API.
- D5.3: Gesture recognition (pinch, pan, tap, swipe) for touch.
- D5.4: Haptics API where available.

Acceptance Criteria
- Examples demonstrate the same gameplay logic across desktop and mobile inputs.

Rationale/Risks
- Developer ergonomics; platform fragmentation risks.

---

## M6 — Tooling and Developer Experience
Objectives
- Make iteration fast and debugging transparent.

Key Deliverables
- D6.1: Dev mode flags (extra asserts, verbose logs) and prod tree-shaking guidance.
- D6.2: Runtime component inspector and property tweaker.
- D6.3: Physics/render debug panels.
- D6.4: Hot module reloading examples and docs.

Acceptance Criteria
- Developers can inspect entities/components and tweak parameters at runtime in examples.

Rationale/Risks
- Shortens feedback loops; avoid heavy runtime overhead in prod.

## M7 — Documentation, Samples, and Education
Objectives
- Turn the repo into a learnable platform.

Key Deliverables
- D7.1: API docs generated from TSDoc/JSDoc.
- D7.2: Progressive tutorial (from "Hello World" to small game) for 2D and 3D.
- D7.3: Framework integration samples (React/Vue/Svelte/Vanilla) with hosted demos.
- D7.4: Advanced techniques examples (streaming worlds, vehicles, post FX).

Acceptance Criteria
- New users can build a basic scene in <10 minutes from docs; CI validates examples.

Rationale/Risks
- Community growth; ongoing maintenance of examples.

## M8 — Cross-Platform and WebXR
Objectives
- Ensure the engine works well on major browsers and devices; explore XR.

Key Deliverables
- D8.1: Compatibility matrix (desktop/mobile browsers and GPUs) with notes.
- D8.2: Responsive/adaptive rendering utilities.
- D8.3: Initial WebXR support path and sample.

Acceptance Criteria
- Public matrix published; WebXR sample runs on at least one supported device.

Rationale/Risks
- Broadens reach; XR APIs evolve quickly.

## M9 — Networking and Multiplayer (Exploration)
Objectives
- Research and prototype deterministic or rollback-friendly approaches.

Key Deliverables
- D9.1: Networking RFC in `docs/rfcs/networking.md`.
- D9.2: Minimal sync demo (host + client) with snapshot interpolation.
- D9.3: Determinism notes and test harness.

Acceptance Criteria
- Prototype demonstrates syncing positions/actions across 2 peers with jitter buffers.

Rationale/Risks
- High complexity; exploration only at this stage.

Objectives

Key Deliverables

- D10.2: WASM spikes for hotspots (physics, math kernels) with FFI boundary notes.
- D10.3: Procedural content generation experiments.

Acceptance Criteria
- Reports with measurements; small demos included.

Rationale/Risks
- Early research; avoid premature commitments.

## Testing Strategy (applies across milestones)
- Unit tests for math, loaders, and adapters.
- Integration tests for cross-engine parity.
- Visual regression tests for rendering outputs where feasible.
- Performance benchmarks with published scenarios and thresholds.
